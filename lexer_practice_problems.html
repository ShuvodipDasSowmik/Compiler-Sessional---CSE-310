Variant A40 minutes10 marks

Binary Constants and Pascal Comments

Extend the existing lexical analyzer with binary integer constants and Pascal-style multiline comments. All previous rules remain unchanged.

1. Binary integer constants

A binary constant begins with 0b or 0B and contains at least one digit from 0 or 1. Valid examples are 0b0, 0B1011, and 0b110010.

InputToken
0B1011<CONST_BIN, 0B1011>

Log valid input as:

Line no 2: Token <CONST_BIN> Lexeme 0B1011 found

If the prefix has no binary digit, or its alphanumeric continuation contains a character other than 0 or 1, consume the whole alphanumeric lexeme and report:

Line no <n>: Invalid binary constant <lexeme>

Examples: 0b, 0B210, 0b101cat. Produce no token and no symbol-table entry.

2. Pascal-style multiline comments

A comment starts with (* (without requiring the space) and ends at the first following *). It may span lines and produces no token.

Line no <start>: Pascal multiline comment ending at line <end> found

At EOF before closure, issue exactly one error and increment the total error count:

Line no <start>: Unfinished Pascal multiline comment

The sequences (, *, *), and multiplication outside a comment must retain their existing meanings. Delimiters in strings and character constants are ordinary content.

Marks

  • Valid binary recognition: 2
  • Whole-lexeme binary errors: 3
  • Pascal comments and operator preservation: 3
  • EOF error and line count: 2

Test cases

Test A1 — valid

int flags = 0b10101;
(* first line
   second line *)
int zero = 0B0;

Additional tokens: <CONST_BIN, 0b10101> <CONST_BIN, 0B0>

Line no 1: Token <CONST_BIN> Lexeme 0b10101 found
Line no 2: Pascal multiline comment ending at line 3 found
Line no 4: Token <CONST_BIN> Lexeme 0B0 found

Test A2 — invalid and unfinished

int a = 0b10201;
int b = 0Bwolf;
(* never
closes
Line no 1: Invalid binary constant 0b10201
Line no 2: Invalid binary constant 0Bwolf
Line no 3: Unfinished Pascal multiline comment
Reveal reference solution

Use an exclusive start condition so the comment terminator and EOF are handled without swallowing unrelated tokens.

%x PASCAL_COMMENT

BINARY_VALID        0[bB][01]+
BINARY_INVALID      0[bB]([[:alnum:]_]*[2-9A-Za-z_][[:alnum:]_]*|$)

%%
{BINARY_INVALID} {
    logOutput << "Line no " << lineCount
              << ": Invalid binary constant " << yytext << "\n\n";
    errorCount++;
}

{BINARY_VALID} {
    string lexeme = yytext;
    logToken("CONST_BIN", lexeme, lineCount);
    tokenOutput << "<CONST_BIN, " << lexeme << "> ";
}

"(*" {
    commentStartLine = lineCount;
    BEGIN(PASCAL_COMMENT);
}

<PASCAL_COMMENT>"*)" {
    logOutput << "Line no " << commentStartLine
              << ": Pascal multiline comment ending at line "
              << lineCount << " found\n\n";
    BEGIN(INITIAL);
}
<PASCAL_COMMENT>\n   { lineCount++; }
<PASCAL_COMMENT>[^*\n]+ { }
<PASCAL_COMMENT>"*"     { }
<PASCAL_COMMENT><<EOF>> {
    logOutput << "Line no " << commentStartLine
              << ": Unfinished Pascal multiline comment\n\n";
    errorCount++;
    yyterminate();
}

Add int commentStartLine; in the declarations block. Place binary rules before CONST_INT and invalid suffix rules. Place the comment opener before separate parenthesis and multiplication rules. In Flex, $ is line-end rather than EOF; a more robust production version can split the bare-prefix cases into explicit 0[bB] rules. For this exercise, use:

BINARY_INVALID  0[bB]([[:alnum:]_]*[2-9A-Za-z_][[:alnum:]_]*|[A-Za-z_][[:alnum:]_]*)
BARE_BINARY     0[bB]

/* order: BINARY_INVALID, BINARY_VALID, BARE_BINARY */
{BARE_BINARY} { /* same invalid action */ }
Variant B40 minutes10 marks

Digit Separators and Documentation Comments

Add C++-style digit separators to integers and documentation line comments to the scanner.

1. Separated decimal integers

A separated integer contains decimal digits with one or more apostrophes between digits. Each apostrophe must have a digit immediately on both sides. Examples: 1'000, 12'345'678. A plain decimal remains CONST_INT.

InputToken
12'345<CONST_SEP_INT, 12345>

The token value has separators removed, while the log retains the source lexeme:

Line no 1: Token <CONST_SEP_INT> Lexeme 12'345 found

A digit-led sequence containing an apostrophe but violating the placement rule is one invalid lexeme. Examples: 1', 2''3, 4'cat. Report:

Line no <n>: Invalid digit separator in <lexeme>

2. Documentation line comments

A documentation comment starts with exactly /// and continues to the physical line end. Consecutive documentation lines are independent comments. Do not include the newline in the match.

Line no <n>: Documentation comment found

Existing // comments continue to use existing behavior. Thus //// note is a documentation comment, since its first three characters are ///. A /// inside strings or chars is not a comment.

Marks

  • Valid separator recognition/value normalization: 3
  • Malformed separator consumed once: 3
  • Documentation precedence over ordinary comments: 2
  • Strings, chars, and line count preserved: 2

Test cases

Test B1 — mixed

int size = 1'048'576;
/// bytes in one mebibyte
int plain = 1000; // ordinary
char quote = '\'';

Additional token: <CONST_SEP_INT, 1048576>

Line no 1: Token <CONST_SEP_INT> Lexeme 1'048'576 found
Line no 2: Documentation comment found

Test B2 — invalid

int x = 12''34;
int y = 7'zip;
int z = 9';
Line no 1: Invalid digit separator in 12''34
Line no 2: Invalid digit separator in 7'zip
Line no 3: Invalid digit separator in 9'
Reveal reference solution 
SEP_INT_VALID    [0-9]+(\'[0-9]+)+
SEP_CANDIDATE    [0-9][0-9A-Za-z_\']*\'
SEP_BAD_MIDDLE   [0-9][0-9A-Za-z_]*\'(\'|[A-Za-z_])[0-9A-Za-z_\']*
DOC_COMMENT      "///"[^\n]*

%%
{DOC_COMMENT} {
    logOutput << "Line no " << lineCount
              << ": Documentation comment found\n\n";
}

{SEP_BAD_MIDDLE}|{SEP_CANDIDATE} {
    logOutput << "Line no " << lineCount
              << ": Invalid digit separator in " << yytext << "\n\n";
    errorCount++;
}

{SEP_INT_VALID} {
    string source = yytext, value;
    for (char c : source) if (c != '\'') value += c;
    logToken("CONST_SEP_INT", source, lineCount);
    tokenOutput << "<CONST_SEP_INT, " << value << "> ";
}

Put DOC_COMMENT before the existing combined COMMENT rule. Put the malformed separator rules before CONST_INT, CONST_CHAR, and identifier-related errors. The valid rule is naturally longer than its plain-integer prefix.

Variant C40 minutes10 marks

Integer Suffixes and Nested Block Comments

Add a restricted family of C integer suffixes and a nestable comment form.

1. Suffixed decimal constants

A decimal integer may be followed by exactly one of u, U, l, L, ul, uL, Ul, or UL. The letters must appear in that order. Examples: 12u, 99L, 500UL.

<CONST_SUFFIX_INT, 500UL>
Line no 3: Token <CONST_SUFFIX_INT> Lexeme 500UL found

Any digit-led alphanumeric continuation that starts like a suffix but is not in the allowed set must be consumed once:

Line no <n>: Invalid integer suffix <lexeme>

Examples: 7lu, 8uu, 10ULong. These constants are not added to the scope table.

2. Nested block comments

A nested comment starts with /*+ and ends with the matching +*/. Another /*+ inside it increases nesting depth; each +*/ decreases depth. The comment ends when depth becomes zero.

Line no <start>: Nested comment ending at line <end> found

At EOF with nonzero depth, produce one error using the outermost start line:

Line no <start>: Unfinished nested comment

Ordinary /* ... */ behavior remains unchanged. Nested comment delimiters in strings/chars are ordinary characters.

Marks

  • Valid suffixes: 2
  • Invalid whole-lexeme suffix recovery: 2
  • Nesting-depth implementation: 4
  • EOF and line counting: 2

Test cases

Test C1 — nesting

int limit = 500UL;
/*+ outer
    /*+ inner +*/
    outer again +*/
int small = 2u;

Additional tokens: <CONST_SUFFIX_INT, 500UL> <CONST_SUFFIX_INT, 2u>

Line no 1: Token <CONST_SUFFIX_INT> Lexeme 500UL found
Line no 2: Nested comment ending at line 4 found
Line no 5: Token <CONST_SUFFIX_INT> Lexeme 2u found

Test C2 — errors

int a = 7lu;
int b = 8unsigned;
/*+ level one
  /*+ level two +*/
Line no 1: Invalid integer suffix 7lu
Line no 2: Invalid integer suffix 8unsigned
Line no 3: Unfinished nested comment
Reveal reference solution 
%x NESTED_COMMENT

SUFFIX_VALID    [0-9]+([uU]([lL])?|[lL])
SUFFIX_INVALID  [0-9]+[uUlL][[:alnum:]_]*

%{
int nestedStartLine = 0;
int nestedDepth = 0;
%}

%%
{SUFFIX_VALID} {
    string lexeme = yytext;
    logToken("CONST_SUFFIX_INT", lexeme, lineCount);
    tokenOutput << "<CONST_SUFFIX_INT, " << lexeme << "> ";
}

{SUFFIX_INVALID} {
    logOutput << "Line no " << lineCount
              << ": Invalid integer suffix " << yytext << "\n\n";
    errorCount++;
}

"/*+" {
    nestedStartLine = lineCount;
    nestedDepth = 1;
    BEGIN(NESTED_COMMENT);
}
<NESTED_COMMENT>"/*+" { nestedDepth++; }
<NESTED_COMMENT>"+*/" {
    if (--nestedDepth == 0) {
        logOutput << "Line no " << nestedStartLine
                  << ": Nested comment ending at line "
                  << lineCount << " found\n\n";
        BEGIN(INITIAL);
    }
}
<NESTED_COMMENT>\n { lineCount++; }
<NESTED_COMMENT>[^*/+\n]+ { }
<NESTED_COMMENT>[*/+] { }
<NESTED_COMMENT><<EOF>> {
    logOutput << "Line no " << nestedStartLine
              << ": Unfinished nested comment\n\n";
    errorCount++;
    yyterminate();
}

Important ordering: put SUFFIX_VALID before SUFFIX_INVALID. Both match an allowed suffix at equal length, so rule priority selects the valid action; malformed longer forms still win by longest match. Put "/*+" before the existing ordinary block-comment rule.

Variant D40 minutes10 marks

Raw Strings and Line Directives

Add backtick raw strings and a simplified source-line directive while retaining all existing quoted strings and preprocessor-error behavior.

1. Backtick raw strings

A raw string starts with ` and ends at the next `. It may span lines. Backslashes have no special meaning, so \n remains two characters. An empty raw string is valid.

InputToken
`a\nb`<RAW_STRING, a\nb> (literal backslash and n)

Log the source content without delimiters, using the starting line:

Line no <start>: Token <RAW_STRING> Lexeme <content> found

At EOF before the closing backtick, produce no token and report exactly one error:

Line no <start>: Unterminated raw string

2. Source-line directives

At the beginning of a physical line, optional spaces or tabs followed by #line, at least one space, and a positive decimal integer form a directive. After the directive's newline, set lineCount to that integer. The directive produces no token.

Line no <old>: Line directive sets next line to <new>

Malformed directives beginning with optional horizontal whitespace and #line are consumed through the line end and reported once:

Line no <n>: Invalid line directive <lexeme>

Examples: #line, #line zero, #line 0, #line 12 extra. A #line not at physical line start is handled by existing rules.

Marks

  • Raw string token and literal content: 3
  • Raw string EOF/line count: 2
  • Valid anchored directive and reassignment: 3
  • Malformed directive as one error: 2

Test cases

Test D1 — valid

#line 40
int value = 7;

second`;

Additional tokens: <RAW_STRING, C:\new\file> <RAW_STRING, first↵second>

Test D2 — invalid

  #line 12 extra
int x = `unfinished
raw
Line no 1: Invalid line directive #line 0
Line no 2: Invalid line directive   #line 12 extra
Line no 3: Unterminated raw string
Reveal reference solution

Turn on beginning-of-line tracking and use a start condition for raw strings.

%option noyywrap
%x RAW

%{
int rawStartLine;
string rawBuffer;
%}

LINE_DIRECTIVE  ^[ \t]*"#line"[ \t]+[1-9][0-9]*[ \t]*\r?$
BAD_LINE        ^[ \t]*"#line"[^\n]*

%%
{LINE_DIRECTIVE} {
    string text = yytext;
    size_t p = text.find("#line") + 5;
    while (p < text.size() && (text[p] == ' ' || text[p] == '\t')) p++;
    int nextLine = stoi(text.substr(p));
    logOutput << "Line no " << lineCount
              << ": Line directive sets next line to "
              << nextLine << "\n\n";
    lineCount = nextLine - 1; /* existing NEWLINE rule makes it nextLine */
}

{BAD_LINE} {
    logOutput << "Line no " << lineCount
              << ": Invalid line directive " << yytext << "\n\n";
    errorCount++;
}

"`" {
    rawStartLine = lineCount;
    rawBuffer.clear();
    BEGIN(RAW);
}
<RAW>"`" {
    tokenOutput << "<RAW_STRING, " << rawBuffer << "> ";
    logOutput << "Line no " << rawStartLine
              << ": Token <RAW_STRING> Lexeme "
              << rawBuffer << " found\n\n";
    BEGIN(INITIAL);
}
<RAW>\n {
    rawBuffer += '\n';
    lineCount++;
}
<RAW>[^`\n]+ { rawBuffer += yytext; }
<RAW><<EOF>> {
    logOutput << "Line no " << rawStartLine
              << ": Unterminated raw string\n\n";
    errorCount++;
    yyterminate();
}

Place the valid directive before the malformed directive. Because both are anchored with ^, they only match when Flex is at beginning of line. Place the backtick opener before the final catch-all rule. The shown valid directive deliberately excludes trailing non-whitespace text.
